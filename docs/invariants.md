# Luminary Invariants

These are non-negotiable. Each one exists because its violation caused a real bug or regression.

## Async / Concurrency

**I-1. Never share AsyncSession across `asyncio.gather` tasks.**
Each concurrent task needs its own session or a `Semaphore(1)` serialiser. SQLAlchemy AsyncSession is not safe for concurrent use.

**I-2. Wrap all synchronous LanceDB *and Kuzu* calls with `asyncio.to_thread`.**
Both are synchronous. Calling either directly in an async function blocks the event loop -- and because the server runs a single worker, it stalls *every* concurrent request, not just the slow one. Measured: a 2ms `/tags/graph` took 8.5s sitting behind one all-library `/graph` traversal, which is why the Map's Tags view appeared to hang. Kuzu is safe to call from a worker thread: `ThreadSafeKuzuConnection` already serializes every `execute()` under an RLock. The same rule covers any long CPU call with no `await` inside it. `parse_node` ran `DocumentParser.parse` inline and froze the loop for a measured 44.9s on a 23MB PDF (3.96s once moved to `asyncio.to_thread`). In `public` mode that is worse than a slow API: the backend also serves the SPA, so its lazy route chunks never arrive and the UI cannot navigate at all -- clicks appear dead while hover still works, because only the server side is stalled. `chunk`, `entity_extract` and `transcribe` are still inline.

**I-3. Always guard Kuzu `get_next()` with `has_next()`.**
`get_next()` raises if no rows exist. Every Kuzu result iteration must call `has_next()` first.

**I-40. What decides shutdown time is the work inside the loop's default executor, not the tasks awaiting it.**
The whole backend suite hung on `master` at `8634011`, ending in `+++ Timeout +++` with no summary line, surfacing in a different test each run. Measured: a 30s `run_in_executor` call held `TestClient.__exit__` for **30.3s with no pending task at all** -- which is what separates this from the task-leak class, and why two rounds of task-draining fixes left it standing.

`asyncio.Runner.close()` ends in `loop.shutdown_default_executor(constants.THREAD_JOIN_TIMEOUT)`, and that constant is **300 seconds**. Every `asyncio.to_thread` call runs in that executor -- I-2 puts LanceDB and Kuzu there, and embedder and GLiNER loads land there too -- so the join waits out whatever is inside one. `with TestClient(app)` runs the app on anyio's blocking portal, whose thread ends in exactly that call, so one fire-and-forget task still embedding a note parks teardown past the 120s per-test timeout and names whichever test owned the client rather than the one that leaked. Nothing awaits those threads through a task, so `_drain_leaked_tasks` cannot see them.

**The same call is on the real shutdown path**, so in-flight `to_thread` work could hold a desktop quit for 300s. `lifespan` ends in `_release_default_executor`, which joins for 20s then detaches: a Kuzu or LanceDB write finishes inside that, a model load is abandoned. Bounding is the safer half of a trade, not free -- unbounded, the desktop supervisor gives up and SIGKILLs, killing a mid-write thread and leaving the Kuzu lock held against the next launch.

`tests/conftest.py` bounds the join at 30s -- above a ~6s GLiNER load, far below the per-test timeout -- and reports every test whose background work outlived it. `tests/test_quit_is_bounded.py` restores the stdlib join before measuring, because the suite's own bound would otherwise satisfy the test whether or not the product had one; `tests/test_testclient_teardown_is_bounded.py` fails CI if the bound is removed, and its second test fails if the work it measures was not actually in flight. **A fixture that gathers cancelled tasks is the same trap in test clothing** -- five teardowns awaited `gather(*pending)` with no timeout while `POST /notes` schedules an embed through `run_in_executor`; `tests/task_drain.py` bounds that and engine disposal in one place. The recurring `test_e2e_upload` timeout is **not** covered: it returns with the loop idle and every aiosqlite worker waiting on an empty queue, which points at a future belonging to a loop that is already gone. Do not read a green run as evidence there.

## FTS5 / SQLite

**I-4. Do not use `WHERE unindexed_col = :val` on FTS5 virtual tables.**
UNINDEXED columns are unreliable for equality filtering when the table is large. Query the shadow content table directly: `notes_fts_content WHERE c1 = :nid` (columns c0, c1, c2 match CREATE VIRTUAL TABLE order). Deletion: `DELETE FROM notes_fts WHERE rowid = :rowid` (rowid-based delete always works).

## Imports

**I-5. Never import at module level inside a service if it creates a circular dependency.**
Use lazy imports inside the method body: `from app.runtime.X import fn  # noqa: PLC0415`. Patch target is then `app.runtime.X.fn`, not the call-site import.

**I-6. Import `get_settings()` at module level in services.**
Never suppress `get_settings()` exceptions with bare `except`. Never lazy-import settings -- it makes the patch target unpredictable in tests.

## LLM / SSE

**I-7. Persist rows before LLM calls in SSE generators; add explicit rollback on error.**
Implicit rollback on session close is insufficient after a generator exception. Add explicit `await session.rollback()` in the error handler.

**I-8. The `done` SSE event payload contains the clean `answer` field.**
The frontend must replace `msg.text` with `payload.answer` on the done event. Streamed tokens include citation JSON fragments -- never leave raw accumulated tokens as the final displayed text.

**I-33. A citation excerpt is a quote the grounding contains. Nothing invents one.**
Measured on shipped 0.6.1 over 10 `book` questions: of 6 citation chips returned, **3 were absent from the chunks the answer was generated from** -- the model's own narration, commentary about the retrieval itself, and real source prose recited from memory that retrieval never returned. All three render indistinguishably from a real quote. All five citation-bearing prompts specified the field as a bare format example, `"excerpt":"..."`, which states a shape and not a provenance. Nothing downstream could tell the difference -- `_enrich_citation_titles` matches on (section_heading, page), never on the excerpt -- while the chunk-derived `source_citations` beside them are safe by construction, so two lists of opposite trustworthiness rendered under one answer.

**Asking the model to copy the quote instead is not the fix.** Prompted to reproduce the passage verbatim and having its excerpt dropped when it did not, the model stopped citing: `citation_coverage` fell 0.750 -> 0.5429 on `book` and 0.872 -> 0.7632 on `paper` against bit-identical retrieval. Trading a fabricated quote for no quote is progress; trading a findable quote for no quote is not.

So the model never reproduces source text. `pack_context_indexed` labels each passage `[S<n>]`, the model cites `{"source":"S1"}`, and `_resolve_marker_citations` fills the excerpt from the chunk that marker names -- verbatim by construction, carrying the deep-linkable `chunk_id`. **Marker numbering must come from the packer**, because grouping, dedup and the token budget decide which chunks reach the prompt; numbering the input list points every citation at the wrong passage. A `quote` the model offers only locates a sentence inside that chunk, never content.

**Which part of the chunk is shown is itself load-bearing.** A chunk is sized for the embedder, so the sentence carrying the claim sits anywhere in it: 12 of 15 measured chips were head cuts, scoring 0.5667 on their displayed excerpt against 0.8667 on the full chunk. `_excerpt_from_chunk` selects by content overlap with the answer, so anything scoring the displayed excerpt -- `citation_support_rate` above all -- measures that selection as much as the citation. Excerpts still arriving as free text stay on the verification path: a contiguous run of 8 normalised tokens must appear in the grounding. `tests/test_qa.py` and `tests/test_context_packer.py` fail CI if a marker resolves to the wrong chunk, an ungrounded excerpt survives, or any prompt stops citing by marker.

**I-34. A flashcard's excerpt is a span of the passage the card was written from, and every card records whether that was checked.**
The review screen prints `source_excerpt` under a heading reading "Source". Measured on a 949-card library: of the 392 cards carrying a checkable quote, **102 (26%) quoted text absent from their document** -- 66 with no recognisable span of it at all -- and nothing in the product could tell them from the 289 that were real. Rewriting the prompt does not fix this (v2 scored 0.7300 factuality against v1's 0.7267): a model asked for a well-shaped card about a familiar text writes what it already believes. Quoting is the part it cannot do from memory, so the check is on the quote.

Two paths were worse than unchecked: `flashcard_audit.fill_gaps` prompted with the section *heading* alone while demanding a `source_excerpt`, so every quote it produced was necessarily invented; `_generate_concept_cards` and `generate_from_graph` had the passage in scope and passed it to neither the gate nor the verdict. A card is written from a passage or it is not written.

`grounding` is four states -- `unchecked | verified | unsupported | unverifiable` -- not a boolean, because "checked and found" and "nothing could be checked" are different answers and 59% of that library is the second; a boolean makes an unaudited deck read clean, which is the defect restated. `unsupported` is reserved for the strong claim: the card produced a quote and that quote is not in the text. `POST /flashcards/grounding/audit` recomputes deterministically with no model in the loop, never overwriting a verdict it cannot re-derive. The match tolerates whitespace, elision and one trailing punctuation character -- 4 of 129 rejections differed by a single closing `.` or `"` on a span otherwise verbatim to ~300 characters -- and nothing more. `tests/test_flashcard_grounding.py` and `tests/test_flashcard_audit.py` fail CI if a fabricated quote is kept, if the gap-fill prompt stops carrying section text, or if a verdict is computed and dropped. See I-33 for the same defect on `/qa`, where the fix differs because a flashcard's quote *is* its evidence.

**I-35. A card's passage is what was in its prompt, and whatever judges that passage is not the model that wrote the card, nor a model shown to agree with everything.**
`flashcards.chunk_id` holds the first chunk of the generation *scope*. Nothing in the code says so, and reading it as "the chunk this card came from" is the obvious mistake: judged against a passage rebuilt that way, a 60-card sample scored `factuality 0.3333` -- and the number was the rebuild, not the cards, since the judge had been shown text not containing the card's own verified quote 56 times in 60. `source_chunk_ids` records the chunks whose text actually reached the prompt, in reading order, and it is the *sampled* subset: past `_CHUNK_CHAR_LIMIT`, `_build_text` keeps a beginning/middle/end window, so recording the whole scope would name text the model never saw. Three states stay distinguishable and none may be read as another: recorded ids, `NULL` (predates the column) and `[]` (supplied text). A card whose passage cannot be rebuilt is **skipped and counted as skipped**, never judged against an approximation.

The second half is derivable only from measurement, and it is the half that will be undone to save memory. Whether an answer follows from a passage is semantic, so this is the one flashcard check needing a model. Screened on 59 live cards with identical passages: `phi4-mini` returned `yes` for 54, `mistral` and `granite3.2:8b` for 53, each agreeing with `qwen2.5:14b` on the pass/fail call 0.41-0.42 -- worse than chance; `gemma3:4b` certified a card that reversed who did what. Only `gemma4` (43/59) and the 14B (19/59) discriminate. So `FLASHCARD_FACTUALITY_MODEL` has **no default**: an unnamed checker does not run and cards stay `unchecked`, which is honest where a rubber stamp is not. Fire every candidate on the four-case probe (supported / reversed / invented / off-topic) **and** at scale -- passing the probe is necessary and demonstrably not sufficient.

Self-judging is refused, and the guard must resolve the model that will actually generate rather than the configured override: the override is empty on the default path, which is exactly where the collision happens. `effective_generation_model()` resolves it; `scripts/smoke/S237.sh` refuses to measure when they collide, and `tests/test_flashcard_factuality.py` and `tests/test_flashcard_passage.py` fail CI if an unparseable verdict defaults to a pass, if a rebuilt passage falls back to `chunk_id`, or if the guard reads the override again.

**I-36. A regeneration reads material the current deck was not written from, that deck is still in the table while it runs, and one call replaces exactly one source.**
"Regenerate (replace)" returned the questions it had just deleted, and the deck came back two cards short of the five it replaced. Nothing was cached: `_filter_chunks_by_classification` leaves 10 of the document's 265 chunks and all 10 fit `_CHUNK_CHAR_LIMIT`, so every run read the same 3,024 characters whatever happened to the deck in between.

**What a generation can ask about is a property of the passage in its prompt.** The lever is which chunks reach it -- not temperature, not an instruction. Listing previous questions under "do not repeat these" is the I-28 anti-pattern in a new place: verbatim questions are exemplars a small model copies. `_passage_not_yet_used` drops the chunks `source_chunk_ids` (I-35) already records and takes the next unread run in reading order. The replacement passage is held to the size of the one it replaces: 14 of 15 cards past the grounding gate capped, against 12 of 15 filling the budget, with neither sharing a question with the deck it replaced -- so the cap costs no novelty.

**A note has no unread material, so its replacement is made different by rejection rather than selection.** Filtering extracted concepts on previous questions was measured useless -- extraction returns whole sentences, which never occur inside a question, so it dropped 0 of 12 and 0 of 11 on two real notes. What fires is the 0.85 cosine test scoped to the note: three rewordings of its own questions scored 0.9284/0.9593/0.9828 against 0.7627/0.7730/0.8248 for new ones.

**A note card records which note wrote it, and only when one note did.** Cards from the `note_ids` path carried no `note_id` -- 75 rows in the dev library -- and `collection_card_filter` matches on it, so "Regenerate (replace)" wiped what the filter could find and stacked a new batch on the rest. A run over several notes records `NULL` rather than naming one: a card that cannot be attributed must not be swept up by a replacement of some other note.

**The order is the other half, and a client cannot get it right.** The near-duplicate filter compares a candidate against the cards the document already has, so deleting the deck first left it comparing against nothing, and a run producing nothing left an empty deck. `POST /flashcards/regenerate` is therefore one request taking exactly one source, so a failed run costs that source's cards and no others. `requested` and `delivered` are both on the wire because they differ -- the quality gate drops cards a backfill cannot always replace. `tests/test_flashcard_regenerate_differs.py` fails CI if a replacement re-reads its own chunks, reads more than the passage it replaces, mis-scopes note dedup, mis-records `note_id`, deletes old cards before new ones exist, lets an empty run delete anything, or hides a short delivery; `scripts/smoke/S243.sh` fails if the endpoint stops taking either source, stops refusing two, or stops reporting the three counts separately.

## Vector Dimensions

**I-9. Note and chunk vectors share one embedding space, whose dimension is a stored property of the corpus rather than a setting.**
The deployed embedder is `bge-small-en-v1.5` and every schema in the space must declare `pa.list_(pa.float32(), 384)`. Notes, chunks and concepts share it, so their vectors are directly comparable. The embedder is therefore not pluggable the way a generation model is: replacing it is a full re-embed behind a migration, and work that makes generation models substitutable must state that it stops here.

**The check is against the embedder, never against a declaration.** `note_vectors_v2` carried a hand-written `NOTE_VECTOR_DIM = 1024`, so a 384-float list could not be cast, every `upsert_note_vector` raised, `embed_and_store_note` logged it "non-fatal" and returned -- and a 61-note library held **zero** note vectors. Semantic note search returned nothing, which is indistinguishable from no matching notes, and had since the table was created. The existing guard compared the table against that constant and both said 1024: a constant is not a check when the constant is what is wrong. One `EMBEDDING_DIM` now feeds every schema, and `tests/test_vector_space_dimension.py` fails CI if a table disagrees **or if the deployed embedder stops producing that many dimensions**. Fixing the declaration does not backfill -- the guard recreates the table, and vectors return only via `ReindexService.reindex_notes`.

## Frontend

**I-10. Every frontend feature must have loading, error, and empty states.**
No blank panels. Loading = skeleton (not spinner blocking the page). Error = inline message per section. Empty = explicit "No X yet" message.

**I-11. Cross-tab navigation uses the `luminary:navigate` DOM event and Zustand store.**
Never use URL hacks or React Router state for cross-tab navigation. Dispatch `new CustomEvent('luminary:navigate', { detail: { tab, filter } })` and handle it in App.tsx.

**I-12. Never use MarkdownRenderer inline in list/table cells.**
Block-level elements (h1, ul) inside a `<td>` break layout. Use `stripMarkdown()` from `src/lib/utils.ts` for single-line text previews.

**I-41. A citation owns the arrival scroll alone, and a scroll inside a `scroll-smooth` container reaches its target only with `behavior: "instant"`.**
Clicking a source chip for a passage in a 23K-word book marked the passage and left it off screen, which reads as no highlight at all. Two causes, neither visible in any one file.

**Three effects scroll on the same navigation**, all `block: "start"`: `DocumentReader`'s `initialSectionId` effect at 100ms, its Read-tab effect at 150ms, and `ReadView`'s own at 200ms. Each is armed by the arrival that also carries the citation, so they fire after the mark has been centred and put the section heading at the top with the passage thousands of pixels below. The passage is inside that section, so nothing is lost by standing them down when citation words are present; a section the reader picks afterwards scrolls normally.

**CSS wins over `behavior: "auto"`.** The reader's scroller carries Tailwind's `scroll-smooth`, so every programmatic scroll animates at a fixed speed and a correction issued mid-flight restarts it. Measured: the mark closed from 7027px to centred over 8.1s of continuous animation, mounting every section it passed, and a 3s retry bound stopped 3535px short -- the reported defect. `behavior: "instant"` lands in one frame.

One scroll is never enough because sections mount lazily: rendering the ones a jump passes changes the height *above* the target, so the scroll must be re-issued until it stops moving. `lib/citation/settleIntoView` is that loop -- arrive, drift, stall and late-render are its four exits -- and `settleIntoView.test.ts` guards the policy. What it delivers is only measurable in a browser: `make verify-citation` reports each chip as marked **and** in view, needs a live model, and is therefore a manual gate. The unit suite has twice said this feature worked while the app showed nothing.

## Quality Gates

**I-13. `make ci` is the gate, and it runs in order: ruff -> layer_linter -> boundary_checker -> pytest -> frontend build -> tsc.**
The order is load-bearing, not cosmetic: a lint error masks the test error underneath it, and a layer violation is a design fault that makes the test result meaningless. Run the cheap check first and fix what it says before moving on; running `pytest` against code `ruff` has already rejected wastes the slow step. Claiming a change is done means `make ci` exited 0 on your machine -- naming the individual commands you ran instead is not the same claim, because `make ci` also runs `check_manifest_schema.py`, `check_manifest_coverage.py` and `check_public_import.sh`, which are the ones people forget. Local green is necessary, not sufficient: GLiNER memory pressure has produced GitHub-only failures that no local run reproduces.

**I-14. `make ci` passing does not mean the app works. `make smoke` is the HTTP contract check.**
`make ci` runs `pytest` against the app in-process; it never starts a server, so it cannot catch a route registered in the wrong order, a router the manifest does not cover, or a response shape the UI reads differently than the test does. `scripts/smoke/all.sh` drives ~180 numbered `S###.sh` scripts against a live backend on :7820 and is the only thing that verifies the wire contract the frontend depends on. A change that adds or alters an endpoint is not finished until it has a smoke script and `make smoke` exits 0. There is no reviewer gate and no `passes=true` flag -- an earlier version of this invariant named both, and neither ever existed in the repo, so any claim of having satisfied them was unfalsifiable. If you want a review, `/code-review` is the mechanism.

**I-32. An eval metric that could not be computed is a failure, never a pass.**
`run_eval.py` scored every generation metric behind `if value is not None`, so a judge that errored or a `/qa` that timed out was skipped and recorded `passed: true` for a run that measured nothing it was asked to. 166 rows in `scores_history.jsonl` were written under that rule, and history is what later deltas are read against. The distinction the gate must keep is **requested-but-uncomputed**, which fails, against **not-requested**, which is a skip: a retrieval-only run legitimately has no faithfulness, while a run that generated answers and could not score them has a hole in it. `_check()` takes `requested=` for exactly this. Never paper over the gap with a default -- no `or 0.0`, no `or 1.0`, no neutral score for a missing verdict. `tests/test_eval_gate.py` fails CI if an uncomputed metric passes, or if a violation stops short of a non-zero exit. See the `eval-integrity` skill.

## Packages

**I-15. Use `uv` only -- never `pip` or `poetry`.**
The lockfile is `uv.lock`. Adding packages: `uv add <package>`. Never run `pip install` directly.

## Privacy & Local-First

**I-16. The default path is local: a fresh install works with no account, no key and no network.**
Ollama is the local runtime today and `WEB_SEARCH_PROVIDER` defaults to `none`. Neither name is the invariant — the invariant is that on-device inference and local search are the default path, and that every cloud provider is an opt-in alternative to a local path that already exists. Never introduce an external API dependency (Tavily, OpenAI, a hosted embedder) without shipping a local-first or privacy-preserving alternative alongside it. A feature that only works against a cloud provider does not ship as a default.

**I-17. Never log or transmit user content (notes, documents) to external telemetry.**
Arize Phoenix and Langfuse must be configured for local use only. Telemetry is for performance metrics and trace structure, not for content mirroring.

**I-18. Explicitly disable telemetry in third-party libraries (e.g., LiteLLM, LangChain).**
Check and disable any "phone home" features in libraries that handle user prompts.

## Concepts & Knowledge Layer

**I-19. Mastery is a stored scalar on the concept row -- never recomputed by text match, never on documents or collections.**
The legacy `chunk.text ILIKE '%name%'` mastery computation is removed. Mastery is written by the assessment pipeline (Study Events) to `concepts.mastery`. Collection/goal numbers are computed rollups, never stored as truth. See `docs/concepts.md`.

**I-20. The concept vector is derived and never a retrieval primary.**
A concept's LanceDB vector (`concept_vectors_v1`) is the 384-dim centroid of its evidence-chunk embeddings, in **chunk space** (bge-small-en-v1.5; chunks, notes, and concepts are all 384-dim in one shared space). Recomputed when evidence changes. Use it only for concept-to-concept and material-to-concept similarity (linking, dedup, candidate seeding, scope resolution). Chunk vectors + FTS5 + graph (RRF) remain the RAG backbone.

**I-21. OKF is a projection, never a transport and never a source of truth.**
LiteLLM carries bytes; OKF carries portable knowledge -- never couple them. OKF files are regenerated from SQLite + Kuzu. A user edit to an OKF file re-enters the system only as an `override` (re-applied after re-parse), exactly like a graph rename/merge. See `docs/concepts.md`.

**I-22. A rejected or edited graph element must not reappear after re-parse.**
Re-parse produces fresh proposals, then `applyOverrides()` re-applies every user decision on top. Rejected concepts/edges and dismissed gaps stay gone (hidden, not deleted). Overrides survive re-parsing -- they are the user's permanent voice over Lumen's guesses.

**I-23. Schema changes are Alembic revisions. The `ALTER TABLE` list in `db_init.py` is frozen.**
`models.py` is the source of truth; `make db-revision m="..."` generates the migration and the server applies it on boot. `db_init.create_all_tables()` is a one-time bridge that lifts pre-Alembic databases to the baseline -- never add to it. Generate revisions ONLY via `make db-revision` (it diffs against a throwaway database): pointed at a long-lived one, autogenerate emits `drop_table()` for real user tables. `tests/test_schema_drift.py` fails CI when models and migrations disagree -- but only because it builds its database by **running the migrations**. It previously built it with `create_all_tables()`, from `models.py`, and compared that against `models.py`: deleting a revision left the gate passing 3/3, which is the exact failure this invariant exists to catch. A drift test whose fixture comes from the source of truth it is checking agrees with itself no matter what the revisions say.

**I-24. Never add code that clears a Kuzu lock or kills a process holding one.**
Kuzu takes an exclusive OS-level file lock that the kernel releases the instant the holder dies (verified against SIGKILL; no lock artifacts on disk). A stale lock therefore cannot exist, so any "release the stale lock" logic can only ever kill a LIVE process mid-write -- which is how a graph database gets corrupted. A held lock means a real second process (another server, or `make concepts`): surface it and let the user stop it. A hand-rolled lockfile is strictly worse than Kuzu's own, because ours *can* go stale.

**I-25. Scope decides WHERE to look, never WHAT was asked.**
`scope='all'|'single'` must not influence intent classification. Telling the classifier to prefer `summary` when scope is the whole library made every bare topic ("Apache Iceberg") a summary request under All-documents while the identical query returned `factual` under a single document. Any node that cannot serve its intent falls through to retrieval (`return {"intent": "factual"}`, which `_route_after_strategy` sends to `search_node`) rather than answering with a placeholder -- a question always gets a real answer.

**I-26. The LLM intent classifier picks a retrieval strategy, never an interactive mode.**
`teach_back`, `socratic`, `notes` and `notes_gap` change what the chat *does* with the message rather than where it looks: teach_back grades it as the learner's own explanation, socratic answers with a question, the notes modes read personal notes instead of the document. A mode is only ever right when the user's phrasing asks for it, and `classify_intent_heuristic` matches that phrasing at 0.95 and returns without calling the LLM. The LLM is therefore only consulted about messages that are *not* mode requests, so any mode it names is a misfire -- an analysis-shaped question came back `teach_back` and was answered with an empty correct/misconceptions/gaps card. `_llm_classify_fallback` chooses from `_LLM_SELECTABLE_INTENTS` only; anything else becomes `factual` (per I-25, a question always gets a real answer). Adding a mode means adding keywords, not loosening the whitelist.

**I-27. One context window per loaded model, resolved from the model and never from the call site.**
Ollama keys its loaded runner on generation geometry and reloads llama-server when a call asks for a different `num_ctx` (~1s idle, far worse under contention). Three per-site windows -- 2048 default, 4096 QA, 8192 generation -- made a single chat turn reload the model twice, and a question asked during ingestion reload it repeatedly.

The *value* belongs to the model and is read from its profile; the *rule* is that exactly one is in force for a loaded model at a time. `model_registry.context_window_for(model_id)` is the only thing that decides a window, falling back to `OLLAMA_NUM_CTX` only for a model with no registry entry. Resolving from the model is **stronger** than a global constant, not weaker: the window is a pure function of the model, so two call sites cannot disagree even by accident. `_summary_num_ctx` resolves the same way, because the same number both requests the window and sizes the summary's input budget -- pinning one to the global would ask for one window, reload the runner, then truncate against the other.

Sizing is a trade, not a maximum: the window must fit the largest single prompt or that prompt is silently truncated, while every serving slot costs a full window of KV cache (I-31). An advertised 256K window is a capability, not a budget. Changing one is not local -- `resident_bytes` is weights plus one KV cache **measured at** `MEASURED_AT_NUM_CTX`, and that footprint decides whether a model is offered on a machine, so re-measure with `scripts/model_footprint.py` rather than editing the number. `tests/test_single_local_context_window.py` fails CI on a second knob, on a call site that *chooses* rather than resolves a window, on any module outside `config.py` and `model_registry.py` reading the global, on a window below the largest prompt, and on one that diverges from its footprint's measurement point.

**I-28. A generation prompt states the shape of what it wants, never the name of a taxonomy.**
Suggested questions were generated by naming the Bloom level ("6 questions at Bloom taxonomy level 5 (Evaluate)"). A label is not a specification: the model pattern-matches the word to the register it has seen it in, and the prompt returned exam papers -- "Evaluate how X's reliance on Y can be advantageous" -- which no reader would type and which trips I-26 by reading as a learner's explanation.

It is an invariant rather than a fix because of portability. What a label resolves to is a property of the model reading it, so a prompt built on one means something different on the next model, and the difference is invisible in any output-quality score. The level selects plain-language guidance in `_LEVEL_GUIDANCE`; the taxonomy word never reaches the model, and the wire key is `depth`, not `bloom_level`. The same rule covers few-shot context: prior questions reach the prompt as bare topic words (`_history_topics`), because injecting them verbatim under "avoid these" hands the model exemplars whose register it copies.

`tests/test_suggestions.py` fails if any taxonomy term reappears in a rendered prompt. That guard covers the suggestions surface only -- `services/flashcard_prompts.py` still enumerates L1-L6 by name, which is the same defect unguarded.

**I-29. The reader never reconstructs prose from retrieval chunks.**
Chunks are sized for the embedder, not the eye: they cut mid-sentence, they overlap, and 90% of them contain no paragraph break at all (261 of 2,599 measured on `frankenstein` + `the_odyssey`). Re-joining them with `\n\n` fabricates a false paragraph break every few hundred characters and duplicates text at every overlap seam. Reading text comes from `sections.body`, which is uncapped; `sections.preview` is a 10,000-char snippet for section lists and flashcard context and is truncated mid-sentence on any longer section, so it is not reading text either. `GET /sections/{id}/content` returns `content_source` (`body` | `preview` | `chunks`) so a degraded tier is visible rather than silent -- `chunks` serves only documents ingested before the column existed, and those must be re-uploaded. `tests/test_section_content_reader.py` fails CI if the reader prefers a lossy tier over `body`. See `docs/universal-reader.md`.

**I-30. A heading is a label the source authored. Nothing invents one.**
The reader draws a section heading only when the stored `heading` is non-empty and reads like a label (`hasAuthoredHeading`); an unlabelled section is rendered without one. Three sites used to fabricate headings and each produced the same artifact -- an oversized `<h2>` printing text that then repeated immediately below it. `universal_parser._segment` stored a whole matched line, which for a transcript IS the utterance (`_is_marker` now sends prose to the body); `_segment_chat_grouped` synthesised "Transcript Part 2: Carol", naming whichever speaker opened the group; `chunk.py` substituted `f"Section {n}"` for every empty heading.

An empty heading is the signal that the source gave none, so nothing downstream may fill it -- `sectionTitle()` still derives a label, but only for the contents panel, which needs an entry to navigate with. Empty-bodied sections are dropped rather than filled with placeholder text: a document's contents page matches the same signature as its chapter openings, so 23 of 49 sections in `the_odyssey.txt` were empty twins that used to read "(Empty Section)". `tests/test_universal_parser.py` and `sectionTitle.test.ts` fail CI if a heading is invented. See `docs/universal-reader.md`.

**I-31. Concurrency comes from the runtime's serving width, and inference cost is call count, not concurrency.**
`OLLAMA_NUM_PARALLEL` is that width. The runtime serves that many at once and queues the rest, so a wider app-side semaphore overlaps nothing -- it moves the wait into the runtime's queue, where it counts against the caller's request timeout instead of being invisible. `diagram_extractor` held a `Semaphore(3)` around a call in a serial `for` loop, so the 3 described nothing.

Measured (M3 Pro, llama3.2, 450-token generations): four callers over **1 slot** share 54.7 tok/s and finish at 4.5/8.9/13.5/17.8s; over **2 slots**, 99.3. Size every semaphore *at* the slot count. Each loaded model has its own runner and slots, so text and vision do not contend.

- **Default 1**, because a slot costs a full `OLLAMA_NUM_CTX` KV cache (896 MiB for a 3B model). Every install path sizes from **physical RAM, never the profile name** -- `install.sh`, `install.ps1`, `bootstrap.sh` and `supervisor.rs` all read `>= 24 -> 2, else 1`; 4 is opt-in through `.env` alone. Keying width to the profile broke it once already: the values were written when `public` meant "under 24GB", and retiring that profile left the 24GB+ line catching 16GB laptops. `tests/test_installer_models.py::test_the_serving_width_band_agrees_across_every_install_path` guards it.
- **`n_ctx_slot` stays 8192 at 2 slots** -- Ollama allocates `num_ctx * num_parallel` and divides -- so raising it violates no I-27.
- **The desktop app has no install step**, so `supervisor.rs` sizes at launch and passes the same number to Ollama *and* the backend; disagreement leaves slots idle behind a narrower semaphore.
- **The runtime does not preempt, but a client cancel frees the slot.** Suggestions admitted one second before a question cost it 48.5s of its 102s time-to-first-token, and a call cancelled at 12.0s was followed by one served in 0.44s. So background work that is cheap to lose and has a real fallback may be abandoned for a waiting user -- `run_yielding_to_interactive`, for suggestions, whose empty return already means "templates answer instead". Enrichment is **not** eligible: abandoning a section summary throws away minutes with no second answer. `tests/test_background_yields_the_slot_to_a_waiting_question.py` fails if a queued call is abandoned or an in-flight one is not.
- **Call count is the real lever.** Prompt eval is ~0.4s against ~16s of decode, so one call per section scales with the book: `web_refs` cost ~50 of DDIA's ~80 enrichment minutes. Reach for fewer calls before more concurrency.

**I-37. A model load is billed to whichever call provokes it, so a slow call is not evidence about the component that reported it.**
Ollama loads a model inside the first request that needs one, and LiteLLM's `ollama/` path does not surface `load_duration`. Every `[perf]` timer in the chat graph is wall clock around an `await`, so the first call after an eviction reports a duration made almost entirely of work that is not its own. Measured on an Intel i7-8850H in a 12GB Docker VM: a 261s question logged `[perf] classify_node LLM fallback took 94.10s`, while llama.cpp's own timings for that call were 189 prompt tokens in 6.05s and 4 generated in 0.59s -- 6.6s of classification behind an 87.5s model load. The classifier was searched twice and was never the cause.

Loading `qwen3.5:4b` on that host measured 9.59s to 155.45s against seconds on the Apple Silicon this app is tuned on, and the spread does not reduce to page cache (35.5s/21.7s dropped against 48.9s/12.7s retained) -- so a load there is not a cost to tune but one to stop paying. **Residency is therefore a measured property of the host, never a platform check**: `warmup._warm_llm` times the first local generation at start-up, and `model_keepwarm` holds the model resident only where that measurement says local inference is expensive. A platform or CPU check would be a guess about the cause rather than a measurement of the effect. `tests/test_model_stays_resident_where_a_reload_is_expensive.py` fails CI if the gate stops being a measurement, if the threshold rises past a real cold load, or if a host that reloads quickly is pinged at all.

**I-38. A drawing primitive larger than its page is a container from a reflowed source, and the measurement that says so must happen before clipping.**
`_cluster_drawings` recovers vector figures from PDFs embedding no raster image -- the only way a LaTeX-authored paper yields figures at all. It read `SQL_Cookbook_2006` as **81 images, 79 of them full pages of body text**. The cause is one line of order: the wash guard clipped each primitive to the page *before* measuring it. Those pages carry one fill rectangle spanning the whole flow, 21,608pt tall on a 792pt page, and clipped it is exactly the text column at 0.765 of page area -- comfortably under `_MAX_FIGURE_PAGE_FRACTION`. Nothing reads as wrong; the evidence identifying the container is destroyed one line above the test. The populations do not overlap and need no tuning: real ink tops out at 0.938x the page box, the smallest container measures 1.20x, so `_MAX_PRIMITIVE_PAGE_SPAN` is 1.05 and not a fitted number.

The cost is not cosmetic -- every recovered figure is a vision LLM call. Those ran 278-305s each against a hardcoded 300s ceiling on a slow host, so the job failed on whichever figure landed above it after 34 minutes, having starved summarisation and flashcard generation of the one Ollama slot (I-31). Seven hours of model time were queued to paraphrase text ingestion had already indexed verbatim, and those paraphrases feed image search, so the work made retrieval worse.

Three things follow, each guarded. **Line shape, not text density, separates a figure from a bordered paragraph**: a paragraph's lines span the box containing them and a diagram's labels do not. Density is wrong -- ResNet's Figure 2 is 0.212 text by area, denser than three of four SQL Cookbook callouts. Across 96 candidate regions the full-width-line share runs 0.000-0.176 for figures against 0.333-1.000 for prose, so `_MAX_PROSE_LINE_SHARE` is 0.25; below `_MIN_PROSE_LINES` the guard refuses to judge, since a figure with one wide caption line scores 1.0. **Extraction retires what it no longer produces** -- deduping on content hash means a re-extract can only add -- but only on a pass that ran *and read everything*: the extractors skip an undecodable object by design, which makes a partial result indistinguishable from "no longer produced", so one transient read failure would delete a stored figure, its PNG and minutes of vision time. `ExtractionOutcome.skipped` carries that out; deliberate rejections are not skips. **A re-extraction supersedes a pending `image_analyze`** whose input set it is about to change, or the analyze runs first and the re-extract waits behind all 77 images it was going to delete. `tests/test_image_extractor.py` fails CI if a page of prose is recovered as a figure, a labelled diagram is read as prose, a failed *or degraded* extraction retires anything, or the survivors of a prune are left with no job to describe them.

The vision ceiling is a host measurement, never a platform check (I-37).

**I-39. A model's residency is what the runtime reports for it, never a process RSS, and every site that sizes the machine reads the same band.**
`scripts/mem_profile.py` records both bases for one profiled ingest, deliberately. Subtracting the backend from the peak leaves 4402.8MB, and that remainder was read as a model's footprint -- `qwen3.5:4b` at "4.31GB" against the 3.21GB Ollama reports, `qwen2.5vl:7b` at "8.77GB" against 6.81GB. Both ~30% high, and the second had no measurement behind it at all: that run never loaded a second model (`max_models_loaded: 1`). The pair then read as 13.07GB, 102% of a 16GB machine, and `MAX_RESIDENT["standard"]` shipped at one resident model. Measured from `/api/ps` with both resident, the pair is **10.02GB**.

On unified memory the runner maps weights the kernel may or may not charge to the process, so `rss.ollama` and Ollama's accounting disagree **by design**: RSS is right for our own process and wrong for a model, so a sum across the two measures nothing. The same pass also read the MB field `peak_ollama_reported_mb` as "3.29GB" -- **every `*_mb` field in that summary is MB**.

**The runner count is a permission, and a permission is not a budget.** `MAX_RESIDENT` says how many runners may load; `fits_together` weighs them at half the machine (`_RESIDENT_SET_FRACTION`), and that is what protects a small desktop. At the 16GB floor both resolve identically, so one slot bought the floor nothing; what it cost is the top of the band, where `standard` runs to 24GB, the pair fits, and a host with room for two was narrowed and told "this profile keeps one model resident". `tests/test_vision_role_resolution.py::test_a_standard_host_with_room_keeps_its_reader` fails CI on that narrowing.

**A fourth site sizes the machine, and it is Rust.** `src-tauri/src/supervisor.rs` sizes the drag-installed DMG, which has no install step to ask in, and no Python test could see it. When the floor moved to 16GB the three shell sites followed and the shell did not, leaving `gb >= 24 => 2, _ => 1`: a 24GB Mac running the bundled app gave Ollama one slot while the backend resolved a text model plus a reader against it, evicting on every switch. `tests/test_installer_models.py::test_the_desktop_shell_agrees_about_the_residency_band` reads the Rust and fails CI if its band drifts from `PROFILE_MIN_RAM_GB` again.

**I-42. A list field from a model can arrive nested, and it is normalised where it enters the system -- because the schema that rejects it fails a whole batch, not one row.**
`misconceptions` came back as `[["Concepts are just tags...", "stored in a list rather than a graph"]]` on a real card, and nothing downstream survived it in two unrelated places. The JSON column stored the nested list, so `TeachbackResultItem` -- declaring `list[str]` -- failed validation and `GET /study/teachback/results` answered **500**; the docked Practice panel polls every card of a run in one batched call, so one malformed card erased the verdicts of every card beside it and the learner watched a finished run report nothing. Separately, `MisconceptionModel.correction_note` is a string column and SQLite refused to bind a list to it, which ran inside the same transaction as the result row and rolled the score back to `status="error"` -- so the visible symptom was a card that scored and then unscored itself.

Normalising at each use site would have fixed neither, because the row was already written. `_string_list` runs in `_parse_teachback_response`, the one place the model's output enters the system, and flattens one level of nesting and stringifies scalars -- reading what the model meant, never inventing a value: a field holding nothing usable yields `[]`, which is what an evaluator naming no misconceptions is saying. `tests/test_practice_run_tally.py::test_list_fields_are_normalised_to_strings` fails CI if a nested list reaches a `list[str]` field again.

**I-43. Adding a free-text field to a JSON prompt is a change to its parse rate, and prose asked for after numbers is what breaks a local model's quoting.**
Folding the teach-back rubric into the evaluation call removed a second LLM call that was grading the learner against the card's own answer rather than the passage. The merged prompt asked for three integers *and* a one-sentence `clarity_comment`, and the sentence was the whole cost: **4/16 submissions scored against 14/16** end to end against the unmerged build on the same library and cards. A card that fails to parse is a learner who wrote an explanation and got nothing back. In isolation the same prompt parsed 12/12 and 9/9 -- **a harness run is not evidence here; only paired servers showed it.** The failures were one family, visible only once the log stopped truncating the raw reply at 200 characters: three of six dropped the opening quote of the comment's value (`"clarity_comment": The explanation is clear...`).

With `clarity_comment` removed and the three integers kept, two independent runs put the merged call at **20/20 and 18/20 against 17/20 and 18/20** -- parse rate held -- while the median wait fell 12.3s to 6.1s and rubric coverage rose from 5/20 to 20/20, because the separate rubric call had been failing ~75% of the time unnoticed. Numbers after prose are safe; prose after numbers is not. Recorded next to `_TEACHBACK_USER_TMPL`: no free-text field joins that call without re-running the parse-rate arm, not just the latency arm.

**I-44. Adding to a deck must read what the deck has not read, and a control that offers to add must ask whether there is anything to add.**
`POST /flashcards/generate` reads the passage its scope names and nothing else, so a second call on the same scope reads the same text and writes the same questions -- which the near-duplicate filter then removes, every one of them. The reader's Practice face offered "add more questions", waited, and answered *"No cards came back. There may be no unused material left here."* on a document with **18 of its 26 passages untouched**. `regenerate` had solved this and generate had not: `_passage_not_yet_used` exists precisely to sweep forward, and only the replace path passed it anything.

Measured on the reported document by the chunks the delivered cards recorded: without the exclusion both cards came from `[1, 2, 9, 10, 11, 13, 17, 18]` -- **exactly the eight chunks the existing deck was written from** -- and one re-asked a question already in the deck. With it, all three came from unread chunks. `avoid_used_material` is opt-in rather than default because a caller naming a passage means that passage, and it is ignored when a selection is supplied: the selection *is* the passage.

The button is the other half. `GET /flashcards/{id}/headroom` reports what no card has been written from, and the panel hides "add more" rather than offering work that cannot succeed. Three cases are deliberately **not** exhausted, because each would hide a control that works: a failed request (an unanswered question is not a no), a document with no chunks, and cards predating `source_chunk_ids` (they claim no passage, so the count over-states what is left, never under-states it). `tests/test_material_headroom.py` fails CI if generate stops excluding used material, if a selection starts being excluded, or if the headroom under-states what is left; `practiceDeck.test.ts` guards the three not-exhausted cases.

**I-45. An evaluator must be told the question, given only the passage the card came from, and never asked for a headline beside the breakdown that explains it.**
Teach-back is the product's one measurement of what a learner understands, and every part of the verdict on screen was reading something other than what the learner was asked.

**It was never told the question.** `_TEACHBACK_USER_TMPL` interpolated the passage, the card's answer and the explanation, and nothing else -- so `completeness`, "how much of what the passage covers the student said", was measured against the whole passage, and `missing_points` named topics the question never raised. The question is in the prompt now, and both are scoped to it.

**And "the passage" was the whole generation batch's.** `source_chunk_ids` records the chunks that were in the *prompt*, so every card from one call carries the same list -- and over `_CHUNK_CHAR_LIMIT` that list is windows sampled from across the document. Measured over the 171 cards whose quote can be located, **38% of the graded text is material the card did not come from** and 41% of those passages jump across the document. The card's own quote picks its window out, because the generation gate has already checked that quote is verbatim: `contiguous_runs` groups the recorded chunks into runs of consecutive `chunk_index` and `run_containing` returns the one holding the quote. Runs, not single chunks -- chunking cuts sentences, so the chunk either side of a quote is its context, and counting only the chunk holding it reads 81% foreign. Where the quote locates nothing the whole passage is kept with its seams marked `[...]`: grading against too much beats grading against nothing, but an evaluator may not read across a gap it cannot see. A chunk that was in a prompt but produced no card stops counting as used, so `material_headroom` (I-44) offers that passage again.

**And the headline was a fourth integer asked for beside the three dimensions, with nothing relating them.** Of 90 stored verdicts carrying a breakdown, **24 (27%) have a headline outside the range their own dimensions bracket**, and **5 learners were told "Good explanation!" and had FSRS schedule the card as known while both dimensions failed**. The panel prints the breakdown beneath the headline, so a reader takes one for the explanation of the other; they were two opinions. `_score_from_dimensions` computes it as `0.6*accuracy + 0.4*completeness`, with a dimension below `_DIMENSION_FLOOR` unable to reach a pass -- accuracy leads because saying something unsupported is worse than stopping short. **Clarity carries no weight**: it is the one dimension with no passage behind it, and it read 6/100 on an explanation whose own `correct_points` named two right concepts. It is still shown, labelled as not counted.

The prompt keeps its three integers **last** (I-43): re-measured on paired servers, **34/40 scored before, 40/40 after**. That says nothing about whether the scores are better -- per-case spread on a 4B model dominates and two runs disagreed on which arm separates real explanations further. The case for this change is what reaches the evaluator. `tests/test_teachback_passage_scope.py` fails CI if a card is graded against another card's window or a discontinuous passage loses its seams; `test_teachback_grounding.py` if the question leaves the prompt or a score is asked for again; `test_teachback_rubric.py::test_score_from_dimensions` if the headline stops being a function of the breakdown; `latestAttempts.test.ts` if the panel reports nothing missing while scoring a learner 5.

**I-46. A count of cards and a count of attempts are different numbers, and every path that resumes a run computes its own -- so the ratio is asserted where it is displayed, not at each counter behind it.**
The docked Practice header reads "N of M reviewed". It has been wrong twice, from two different counters, and the second shipped *after* the first was fixed and guarded.

The first read **"4 of 3 reviewed"**: the in-run tally incremented per submission, so a card answered again counted twice. That became `countedCards`, a set of ids.

The second read **"30 of 15 reviewed"** on a session holding 30 attempts across 5 cards. Resuming does not use that tally at all -- `studySessionService.reattach` seeds the count from `Math.max(prevResults.length, remaining.answered_count)`, and those terms are in **different units**: `answered_count` is a set of flashcard ids restricted to the plan, `prevResults` is one row per *attempt*, so the max reliably picks the wrong one. Three lines below, `onResumeLoaded` seeds `countedCards` from `new Set(prev.map((r) => r.flashcard_id))` -- the same question answered correctly in the same function. Neither site reads as wrong alone. The max itself is load-bearing and must stay: without it a card answered and then regenerated out of the plan vanishes from the tally. Both terms just have to be distinct cards. A sweep found a third site: `end_session` tallied `cards_reviewed = len(events)`, so a card graded twice counted twice there too.

**A continuous run makes this class inevitable**, which is why the guard is structural rather than per-counter: one session per document per mode accumulates attempts indefinitely, so any counter growing per submission diverges from the plan -- silently, because both numbers look plausible until one passes the other. `verify-dock`'s `checkProgressHeader` parses the rendered ratio and fails if the numerator exceeds the denominator, on a fresh run *and* a resumed one; `studySessionService.test.ts` fails CI if the resume tally counts rows again, or if the max stops covering a result whose card has left the plan.

**I-47. A run's plan may name cards that no longer exist, and a deleted card is neither progress nor work outstanding -- it leaves both sides of the ratio.**
Reported from the reader as "7 of 8 reviewed" on a document holding **three** cards. Replacing the deck deletes the cards an open run planned, `planned_card_ids` keeps their ids, and their `review_events` stay behind too, because an event records a review that happened. `GET /sessions/{id}/remaining-cards` then counted those five ids as answered, dropped them from `cards` because no row loads, and returned `planned_count` over the raw plan -- so `answered + remaining == planned` and the inflation was invisible to every reader. The client cannot repair it: `reattach` reconciles with `Math.min(planned_count, answered + live remaining)`, and both terms inflate together.

The fix is one line of definition: **planned means planned AND still there.** The endpoint loads every planned card once, keeps the ids that resolve, and computes both counts over that list.

Two things made this survive the sweep that produced I-46. It is not an arithmetic error -- 7 <= 8, every counter agreed with itself, and the ratio check passed. And the harness read its denominator from the same endpoint that produced the header, so the system was verifying itself (`product-integrity.md`); `verify-dock` now takes the cap from `GET /flashcards/{document_id}`, which the header is not built from. `test_practice_run_tally.py::test_a_replaced_deck_leaves_the_run_no_phantom_progress` fails CI if a deleted card counts on either side.

The client-side half: `endOpenSessionsForScope` closed only the newest open run per mode, because `GET /sessions/open` returns one row. A second open run then survived a replacement, was adopted by the panel, and had fresh cards appended to its dead plan.

**I-48. One generation call may not ask the same thing twice, and the answer is what shows it -- but only within that call. Widening the same test to the deck refuses a fifth of every document's cards.**
A reader replaced a deck and got three cards, two asking the same thing. The dedup check ran, measured them at **0.8014**, and passed them: its bar is 0.85. Across the 221 real generation calls in this library (549 cards), the question bar has caught a within-call repeat **zero times** -- it is not a check on what one call produces.

**The second axis is the answer.** That pair scores 0.7614 on answers, so `_repeats_this_call` refuses a candidate clearing question >= 0.78 **and** answer >= 0.75 against a card already accepted from the same call. Both bars are bracketed by real cards named next to the constants: the ramble pair at 0.8014/0.7614 is refused, and "Why do massive-scale corpora require hard choices regarding storage costs?" against "Why are lexical search and dense retrieval considered complementary?" at 0.7890/0.7410 is kept.

**The scope is the measured part and must not be widened.** Applied to the whole existing deck the identical bars refuse a **median 19.1%** of every document's cards (308 of 947), and the sample is full of plainly distinct cards -- a deck accumulates legitimately similar cards over months of separate runs; one call reading one passage does not. Within a call the rule costs **21 of 549 cards (3.8%)**. Do not lower the deck's 0.85 to reach these cases either: **1,396 pairs** here sit in [0.80, 0.85) on questions alone and most are different cards. Dedup drops are not backfilled, so over-rejection is paid in cards the learner never receives.

**And the check could not fire at all on an empty deck.** Candidates were encoded only `if candidates and existing_vecs is not None`, so comparing a batch against *itself* depended on there already being cards -- the first generation on a document was the only run that could hand back the same question twice (a check that cannot fail is not a check). `test_flashcard_duplicate_rule.py` fails CI if either bar moves without its bracketing cases, if the joint test reaches the deck, or if a first batch stops being checked against itself.

**I-49. A pair of one entity is not a relationship, and a co-occurrence edge gains weight fastest on whatever a document repeats most -- so the meaningless pair sorts first.**
Reported from the reader as a card asking *"In the provided context, how are the two mentions of Ulysses connected?"* -- a question with nothing to answer. `generate_from_graph` takes the top-weighted entity pairs and orders the model to write "the relationship between 'X' and 'Y'"; the top pair in `the_odyssey` was **('ulysses', 'ulysses') at weight 62.0**, more than three times the next.

`write_entity_graph` groups `canonical_entities` by chunk, and that list carries **one row per mention, not per entity** -- a chunk naming Ulysses twice put his id in the list twice, and `combinations(chunk_ent_ids, 2)` paired him with himself. Weight increments on every repeat, so the self-loop grows fastest exactly where a document has a protagonist: **8,235 of 74,376 CO_OCCURS edges (11.1%)** are an entity with itself, at the top of every `ORDER BY r.weight DESC`. The prerequisite and tech-relation loops *in the same function* already guarded `id_a != id_b`; only co-occurrence did not. Deduplicating the ids also fixes edge direction, which was mention order: `('minerva','ulysses')` at 19.0 sat beside `('ulysses','minerva')` at 17.0 -- one pair, two edges, two chances to ask one question.

**Guarded in four places, because three of them are already wrong in every existing library.** Documents on disk will not be re-ingested, so `get_co_occurring_pairs_for_document` excludes self-pairs and folds both directions on read; `add_co_occurrence` refuses the edge whoever writes it; `generate_from_graph` drops a pair whose two *names* match, since names are what the prompt shows and two ids can share one. RELATED_TO carries the same read guard although it holds **zero** edges here -- worth knowing on its own: every graph card in this library came from the co-occurrence fallback, so the fallback is the path. `test_entity_cooccurrence.py` and `test_graph.py` fail CI if a mention list pairs an entity with itself, if a stored self-pair is handed out, or if one pair is returned twice; `test_flashcard_from_graph.py::test_an_entity_is_never_asked_how_it_relates_to_itself` fails if such a pair reaches the model.

**I-50. A question that points at its source cannot be answered away from it -- and a gate listing phrasings is always missing the one the model just wrote, so key it on the referent.**
The prompt has forbidden this since it was written: *"The question must stand alone -- never say 'in this passage', 'according to the text', or 'the author'."* The gate enforcing it held sixteen literal phrasings. The reported card said **"the provided context"**; the list held `"this context"`. Across 1234 library cards, **31 point at their source in wording no entry covers** -- "the text suggests", "according to these notes", "in the provided text". A card is shown on its own, so this is not a style defect: the subject of the question is not on screen.

The rule matches the **referent** instead -- a noun naming the material (context, passage, text, excerpt, document, notes, article, essay, chapter, section, book) under something that points at it: a demonstrative (`this passage`), a hand-over qualifier (`the provided text`), an attribution preposition (`according to the context`), or the source as the one speaking (`the text suggests`).

**Bare "the <noun>" is deliberately not a trigger, and that exception is the measured half.** These nouns are ordinary vocabulary: *"Why must a Cross-encoder receive both the query and **the document**?"* is an IR question and *"beyond **the context** window limit"* is a model's input budget -- both good cards, and both refused by a determiner-plus-noun rule. So is a topical qualifier: a source noun taking "of" or "for" names a subject, and without that exception 26 further library cards go, including *"What are CoW and MoR **in the context of** modern data lakehouses?"*. As written the rule refuses **35 of 1234 cards (2.8%)**; all 31 newly caught were read individually and none is answerable alone. The sixteen phrasings stay beside it -- they catch "this example", "the scenario" and "the author", which no referent rule covers. `test_flashcard_quality_gate.py` fails CI if a pointing question passes, or if a source noun used as vocabulary is refused.
